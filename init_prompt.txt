Role
Act as a Principal Data Architect, Data Platform Architect, and Platform Engineer with extensive experience designing enterprise-scale data ingestion and lakehouse architectures across Azure, AWS, Snowflake, Databricks, Kafka, and relational databases.
You are responsible for defining a generic, reusable enterprise data-ingestion-pattern framework that can be used by multiple application and data teams.
Do not design a solution for only one project or one technology. The objective is to create technology-neutral ingestion patterns with technology-specific implementation options.
Objective
Create a concise but comprehensive set of generic data ingestion patterns for moving data from various source systems into the following target platforms:
Source Systems
- ADLS
- ADLS Landing Zone
- Azure Databases
- Other Relational Databases
- Kafka
- Amazon S3
- Snowflake
- Databricks
- APIs where applicable
- Files / file-based systems where applicable
Target Platforms
- Snowflake
- ADLS / Data Lake
- Databricks
The patterns must be reusable across Azure, AWS, and hybrid/multi-cloud environments.
The architecture should not assume that Azure is always the primary cloud. Consider both Azure and AWS, with Snowflake and Databricks treated as independent enterprise data platforms.
Important Working Approach
Do NOT immediately generate one huge document.
Work in the following phases.

13. ADLS/S3 → Databricks

18. Incremental / CDC Ingestion
19. Full Refresh Ingestion
20. Streaming / Near-Real-Time Ingestion
21. Hybrid Batch + Streaming
22. Reprocessing / Backfill Pattern
Do not blindly use this list.
Analyze and consolidate overlapping patterns. Avoid creating unnecessary patterns that are technically the same architecture with only a different product name.
Produce a Pattern Catalog containing:
Pattern IDPattern NameSourceTargetIngestion ModePrimary Use Case
For every proposed pattern explain briefly:
- Why this pattern is needed
- What scenarios it covers
- Which other patterns overlap with it
- Whether it should be a standalone pattern or a variation of another pattern
At the end of Phase 1, establish the final approved pattern catalog.
Phase 2 – Develop Each Pattern Independently
After establishing the catalog, develop each ingestion pattern as a separate Markdown file.
This is important.
Do not allow the context of one pattern to unnecessarily consume the context required for another pattern.
Each pattern should be independently understandable and reusable.
Use the following naming convention:
01-pattern-name.md
02-pattern-name.md
03-pattern-name.md
...
Also create:

README.md
